# アーキテクチャ(ホスティングと会話の受け取り方)

最終更新: 2026-10-28

## 決定事項

- ホスティングにはCloudflareを使う。
- ユーザーは、Botへのメンションと、Botのメッセージへの返信で会話する。Botのメッセージへの返信には、メンションがなくても会話の続きとして応答する。
- 既存のメッセージに返信しながらBotをメンションすると、返信先のメッセージについて聞ける(例:「これどういう意味?」)。
- メッセージの右クリックメニュー(アプリ→「Bobertに聞く」)からも聞ける。詳しくは[Botの振る舞い](behavior.md)を参照。
- 特権インテント「Message Content」を必須とする。
  - 専用Bot(100サーバー未満)なので、Developer Portalで有効にするだけでよく、審査は不要。
  - インテントなしで動く代わりの動作は作らない。
- Discordとの常時接続(Gateway)はDurable Objectで持つ。discord.jsは使わない。
- Gatewayへの接続処理は自作する。
- 再開できずに取りこぼしたメッセージは許容する。
  - 切断はある程度定期的に起きるが、ほとんどは数秒〜数十秒で再開できる。その間のイベントはDiscordが送り直す。
  - 取りこぼしが起きた時刻は記録し、頻発するようなら後から拾う仕組みを検討する。
- 会話の文脈として、返信のつながり(会話)全体を毎回AIに渡し、費用はプロンプトキャッシュで抑える。
  - 加えて、AIに過去メッセージを参照する道具(意味で検索、時系列で読む、チャンネルの一覧)を渡す。AIが必要と判断したときだけ、今いるチャンネルと、サーバーの公開チャンネルの過去のメッセージを参照する(RAG)。
  - このため、公開チャンネル(@everyoneが見られるチャンネル)の全メッセージを保存する。権限付きのチャンネルのメッセージは保存しない。詳しくは「会話の文脈と過去の発言の保存」と「サーバー全体の公開チャンネル」を参照。
- キーを登録していないユーザーにメンションされたら、登録方法を短く返信して案内する。サーバーに使える寄付があれば、寄付で答える([LLM利用コスト](llm-cost.md)「クレジットの寄付」を参照)。
- DMでの会話は後回しにする。まずはサーバー内のメンションと返信だけに対応する。

Discordは、通常のメッセージやメンションをGateway(常時接続のWebSocket)でしか配信しない。HTTPで届くWebhookイベントには含まれないため、Gatewayに接続し続ける部品が必要になる。

## 構成(案)

| 役割                                                          | Cloudflareの機能                       |
| ------------------------------------------------------------- | -------------------------------------- |
| Gatewayへの常時接続。メッセージの受信と、応答すべきものの判定 | Durable Object(1つ)                    |
| LLMの呼び出しと、Discordへの返信の投稿                        | Queues(1回あたり最大15分)とWorker      |
| スラッシュコマンド、モーダル、右クリックメニュー              | HTTPのInteractionsで受ける             |
| OpenRouterのOAuthコールバック                                 | Worker                                 |
| ユーザー設定、暗号化したキー、寄付の保存                      | D1。暗号鍵はWorkerのシークレットに置く |
| メッセージの保存と検索(RAG)                                   | 本文はD1、検索用のベクトルはVectorize  |
| 検索用のデータ化(埋め込み)                                    | Workers AI                             |
| `/import`の進み具合の表示(5秒おきの書き換え)                  | Durable Object(サーバーごとに1つ)      |
- Workersの有料プラン(月$5)を使う。無料プランはCPU時間が1リクエストあたり10msしかなく、足りない可能性が高い。
- D1は北米東部(`enam`)に作る。処理の多くはDiscordのある北米で動くため、データベースも近くに置く。
- コードはTypeScriptで書く。Workersの実行環境はNode.jsではないため、discord.jsなどのNode.js向けライブラリは使えない。型定義には`discord-api-types`を使える。
- LLMの呼び出しにQueuesを使うのは、Workerが応答を返した後に処理を続けられるのが30秒までのため。
- スラッシュコマンドと右クリックメニューには、3秒以内に最初の応答が必要。先に保留の応答を返し、15分以内に本文へ書き換える。
- AnthropicのTypeScript SDKは、Cloudflare Workersを公式にサポートしている。OpenRouterはHTTPで呼ぶ。

## Gateway接続処理(自作)の設計

### 役割

- Gatewayへの接続を1本保ち、イベントを受け取る。受信専用で、Discordへの投稿は普通のHTTP APIで行う。
- `MESSAGE_CREATE`は、保存のためにすべてQueueに渡す。保存には検索用のデータ化も含む。保存するのは、公開チャンネルのメッセージだけ(保存の処理で確かめる)。`/import`の進み具合のメッセージは渡さない。
- そのうち応答すべきもの(Botへのメンションなど)は、応答のためにも渡す。
- Bot自身の投稿と、ほかのBotの投稿には応答しない(保存はする)。
- メッセージの編集(`MESSAGE_UPDATE`)と削除(`MESSAGE_DELETE`、`MESSAGE_DELETE_BULK`)のイベントも受け取り、保存した内容をDiscordに合わせる。
- サーバー・チャンネル・スレッド・ロールのイベント(`GUILD_CREATE`、`CHANNEL_CREATE`・`UPDATE`・`DELETE`、`THREAD_CREATE`・`UPDATE`・`DELETE`・`LIST_SYNC`、`GUILD_ROLE_UPDATE`)も受け取り、公開チャンネルかどうかの記録に使う(「サーバー全体の公開チャンネル」を参照)。

### 接続の設定

- **接続先:** Get Gateway Bot(`GET /gateway/bot`)で取得したURLに、`?v=10&encoding=json`を付けて接続する。v10は実装時点(2026年10月)の最新版。
- **圧縮:** `zlib-stream`や`zstd-stream`は使わない。まずは単純さを優先する。
- **インテント:** `GUILDS`(1)、`GUILD_MESSAGES`(512)と、特権の`MESSAGE_CONTENT`(32768)。`GUILDS`は特権ではなく、チャンネル・スレッド・ロールの変更を受け取るために使う。DMに対応したら`DIRECT_MESSAGES`(4096)を足す。
  - インテントを変えると、Resumeでは反映されず、新しい接続(Identify)が要る。デプロイの後に、管理用エンドポイントで止め、4分ほど待ってから始め直す。Gatewayを持つDurable Objectは、デプロイしても前の版のまま動き続けることがあり、止めてしばらくたつと片付けられて、次に始めたときに新しい版で動くため。
- **Message Contentが無効な場合:** Developer Portalで有効になっていないと、Gatewayは切断コード4014で切れる。このときは再接続せず、管理者に通知する。

### Durable Objectのストレージに保存するもの

- 動いているかどうか(管理用エンドポイントのstartとstopで切り替える)
- セッションIDと再開用URL(READYで受け取る)
- 最後に受け取ったイベントの通し番号(seq)
- BotのユーザーID(READYで受け取る)
- 最後に受信した時刻。切断時と、30秒ごとの見回りで保存する。次につながったときに、切れていた時間を記録するため
- Identify、Resume、再接続の回数と、最後の切断の時刻とコード

WebSocketの接続、ハートビートのタイマー、最後にACKを受け取った時刻は、メモリだけに持つ。

新規接続(Identify)は24時間に1000回まで。Identifyの前にGet Gateway Botで残りの回数を確かめ、尽きていたら管理者に知らせて、回復するまで待つ。接続先URLもこのときに受け取る。

### 接続の流れ

1. 接続すると、Hello(op 10)でハートビートの間隔が届く。
2. 再開できる情報があればResume(op 6)を送り、なければIdentify(op 2)を送る。
3. 最初のハートビート(op 1)は「間隔×0〜1のランダム値」後に送る。以降は間隔ごとに、最後のseqを付けて送る。
4. Discordからop 1が届いたら、すぐにハートビートを返す。
5. 次のハートビートまでにHeartbeat ACK(op 11)が来なければ、接続が死んだとみなす。1000と1001以外のコードで閉じ、Resumeする。
6. READY(op 0)で、セッションID、再開用URL、BotのユーザーIDを保存する。
7. イベント(op 0)を受け取るたびに、seqを更新して保存する。

### 切断時の対応

| 状況                                | 対応                                                                                                                |
| ----------------------------------- | ------------------------------------------------------------------------------------------------------------------- |
| Reconnect(op 7)                     | 閉じて、再開用URLにつなぎ直してResumeする                                                                           |
| Invalid Session(op 9)で`d`が`true`  | Resumeする                                                                                                          |
| Invalid Session(op 9)で`d`が`false` | セッション情報を消し、数秒のランダムな待ちを入れてから、Identifyで最初から接続する                                  |
| 切断コード4004、4010〜4014          | 再接続しない。トークン、インテント、Message Contentの有効化などの設定の誤りなので、エラーを記録して管理者に知らせる |
| その他の切断                        | 待ち時間を指数的に延ばしながら(上限あり)再接続し、Resumeを試す                                                      |

### 退避とデプロイへの備え

- 外向きのWebSocketは休止(hibernation)できず、退避されることがある。接続が開いていても、退避を防げる保証は最大15分。デプロイのたびにも切れる。
- タイマー(`setTimeout`)はメモリと一緒に消えるので、Durable Objectのアラームを30秒ごとに設定し、接続の有無と最後の受信(ハートビートのACKを含む)の時刻を確かめる。接続がなければ、保存した情報でResumeし、できなければIdentifyする。
- seqの保存が遅れると、Resumeの後に同じイベントが再送されることがある。メッセージIDで重複を除き、同じメッセージに2回返信しない。
- 位置のヒントに「北米東部」(`enam`)を指定し、DiscordのGateway(米国東部)の近くに置く。ヒントは努力目標で、保証はない。

### Queueに渡す内容

保存用と応答用の2つのQueueに分ける。
- **保存用(作成と編集):** メッセージID(重複除去のキー)、チャンネルID、サーバーID、投稿者のIDと表示名、Botかどうか、本文、返信先のメッセージID、添付ファイルの情報、投稿と編集の時刻
- **保存用(削除):** チャンネルIDと、消えたメッセージのID
- **保存用(チャンネルの記録):** サーバーID、受け取った時刻、@everyoneの権限、作成・変更されたチャンネルとスレッドの情報(親のチャンネル、種類、名前、年齢制限、@everyoneへの上書き)、削除されたもののID、サーバーの全チャンネルのID(`GUILD_CREATE`のとき)。1件の大きさの上限(128KB)に収まるよう、チャンネルは200個ずつに分ける
- **応答用(応答が必要なものだけ):** メッセージID、チャンネルID、サーバーID、投稿者ID

### 起動と監視

- **起動と停止:** Workerの管理用エンドポイントから操作する。`ADMIN_TOKEN`をBearerトークンとして付ける。起動後はアラームで動き続け、デプロイや退避で切れてもResumeでつなぎ直す。
  - `POST /admin/gateway/start`: 接続を始める。接続中なら何もしない
  - `POST /admin/gateway/stop`: 接続を止める。セッション情報を消すので、次の起動はIdentifyから
  - `GET /admin/gateway/status`: 状態を返す
- **状態確認:** statusで、次のものを見られる。
  - 動いているか、接続しているか
  - セッションIDと最後の通し番号
  - 最後にACKを受け取った時刻
  - 再接続、Resume、Identifyの回数と、最後の切断の時刻とコード
- **記録:** 次のものを記録する。ログの各行には時刻が付く。
  - 切断(切断コードと、つながっていた時間)
  - Resumeの失敗
  - つなぎ直したとき(切れていた時間)
  - Resumeできずに新しいセッションで始めたときは、取りこぼしが起きた可能性のある時間帯(`possible_message_loss`)。後から確かめられるようにするため
- **Botのトークン:** Workerのシークレットに置く。

### 規模が大きくなったとき

2,500サーバー以上に入るとシャーディング(接続の分割)が必須になる。そのときは、シャードごとにDurable Objectを分ける。

### テスト

- やり取りの判断(`src/gateway/session.ts`)は、通信やタイマーから切り離してある。偽の接続側を使って、次の場合の動きを確かめる。
  - Hello後のIdentifyとResume
  - READYでの保存と、イベントの受け渡し
  - ハートビートと、ACKが返らないとき
  - op 7
  - op 9(`d`が`true`のときと`false`のとき)
- 切断コードの分類と、応答すべきメッセージの判定も単体で確かめる。
- 開発用の環境でデプロイし直し、Resumeで再開できることを確かめる。

### 費用

- 24時間接続しても、Durable Objectの稼働時間は月約33万GB-秒で、有料プランに含まれる40万GB-秒の範囲内。
- 受信したWebSocketメッセージは、20件で1リクエストとして数えられる。
- アラーム(30秒ごと)は、1回ごとに書き込み1行として数えられる。月約8.8万行で、含まれる量(月5,000万行)の範囲内。
- 全メッセージを保存しても、小規模なサーバーなら、D1、Queues、Vectorizeは含まれる量の範囲内。
- 全体で月約$5の見込み。

## 会話の文脈と過去の発言の保存

- **保存するもの:** 公開チャンネル(スレッドを含む)の全メッセージ(Botに話しかけていない発言も含む)と、Botの返答。権限付きのチャンネル(非公開スレッドと年齢制限のチャンネルを含む)のメッセージは保存しない(下の「サーバー全体の公開チャンネル」を参照)。参加やピン留めの通知などのシステムのメッセージは、会話ではないので保存しない。Botが動き出す前のメッセージは、`/import`で取り込む(下の「過去ログの取り込み」を参照)。
- **保存先:** リアルタイムで受け取ったメッセージも、取り込んだ過去ログも、同じ場所に入れる。メッセージIDで重複を防ぐ。
  - **D1:** メッセージ本文と付随情報(メッセージID、チャンネルID、サーバーID、発言者のIDと名前、時刻、返信先、メンションされた人の名前、添付の情報、Embedの中身、コマンドへの返答の情報)。サーバーで見えている名前(人ごとに、最後に分かったもの)、チャンネルごとの過去ログ取り込みの進み具合、`/import`の回、会話の要約、チャンネルとスレッドの記録(公開かどうか)、サーバーごとの@everyoneの権限もD1に置く。
  - **Vectorize:** 1メッセージにつき1つのベクトル。ベクトルのIDはメッセージIDにして、D1の本文とひも付ける。チャンネルごとに名前空間(namespace)を分け、発言者ID、時刻、サーバーIDをメタデータとして付ける。サーバーIDは、サーバー全体を探すときの絞り込みに使う。本文が空のメッセージ(添付だけなど)は、ベクトルにしない。
  - **容量:**
    - D1は1データベース10GBまで。1件0.5KB程度なら、約2,000万件入る計算。
    - Vectorizeは1索引2,000万件まで。
    - 超えそうになったら、サーバーごとにデータベースと索引を分ける。
- **検索用のデータ化(埋め込み):**
  - Workers AIの多言語対応の埋め込みモデル(bge-m3、1024次元)を使う。費用は運営者が負担する。
  - ベクトルにする文は、本文に続けてEmbedの中身(文字の部分)を入れる。メンションは名前に置き換え、Bobertの返答の末尾の注記は外す。
  - ベクトルにするのは、新しいメッセージと、本文かEmbedが変わったものだけ。リンクのプレビューは、投稿の後に編集の通知で届くので、本文が同じでもEmbedは変わる。
  - bge-m3は100万トークンあたり約$0.012で、1日ごとの無料枠もある。全メッセージが対象でも、小規模なサーバーなら月数セント程度の見込み。
- **AIに渡すもの:**
  1. 返信のつながり(会話)全体。件数の上限は設けない。長くなったら自動で要約する(下の「長い会話の自動要約」を参照)。
  2. 過去メッセージを参照する道具(意味で検索、時系列で読む)。AIが必要と判断したときだけ使う(下の「過去メッセージを参照する道具」を参照)。
- **検索の範囲:** 今いるチャンネルと、サーバーの公開チャンネル。権限付きのチャンネルの内容が、ほかのチャンネルでの返答に出ることはない(下の「サーバー全体の公開チャンネル」を参照)。
- **保存期間:** 削除されるまで無期限。
- **削除の連動:** Discordでメッセージが削除されたら保存分も消し、編集されたら更新する。`/delete`で消えるのはキーと設定だけ。
  - チャンネルやスレッドが削除されたら、その保存分も消す。チャンネルを削除しても、メッセージごとの削除の通知は届かないため。
  - 処理のやり直しで順番が入れ替わっても、古い版で上書きしない。削除したメッセージも保存し直さない(そのために、削除したメッセージのIDを1日だけ残す)。
- **会話の履歴の読み方:** 公開チャンネルの全メッセージを保存しているので、返信のつながりは、Discordに問い合わせずにD1から読む。権限付きのチャンネルでは、保存していないので、Discordから読む。
  - 保存していないもの(Botが動き出す前のものや、保存の処理がまだ済んでいないもの)は、Discordから読み、保存にも回す(下の「過去ログの取り込み」の、読んだ分だけ取り込む)。
  - 話しかけたメッセージ自体は、Discordから読む。保存より先に応答の処理が動くことがあり、消されていないかも確かめたいため。
  - 保存した添付のURLは期限付き(約24時間)。AIに渡す画像は、期限が近ければ、Discordから読み直して取り直す。読み直せなかった(消えていた)メッセージは、会話から外す。
  - 返信のつながりの始まりが「Bobertに聞く」の返答なら、説明の対象のメッセージを会話の最初に入れる。Interactionへの返答は「返信」ではないので、返信のつながりからはたどれないため。
- **件数の上限:** 返信のつながりには、件数の上限を設けない。要約した位置まで読んだら止め、それより前は要約で渡す(下の「長い会話の自動要約」を参照)。Discordから1件ずつ読むのは、1回の返答で100件までにする(保存したものから読む分には上限はない)。
- **会話の並べ方:**
  - Bobertの発言はAIの発言、それ以外は、時刻と名前を付けた人の発言として渡す。例: `[2026-10-27(火) 14:05] Bob: これどういう意味?`
  - Bobertの発言には、時刻を付けない。AIが返答に時刻を書き始めないようにするため。
  - メンションは名前に置き換える。返答の末尾に添えた注記(`-# `で始まる行)は外す。
  - Embed(ほかのBotの投稿の埋め込みや、リンクのプレビュー)の中身は、本文の後に`[Embed]`を付けて書き添える。提供元と作者、タイトル、説明、項目、フッターを、長さの上限を設けずに渡す(Discordの上限は6000文字)。
  - ほかのBotの発言は、名前にBotであることを書き添える。コマンドへの返答なら、どのコマンドを誰が使ったかも書き添える。例: `おひるん！(Bot。.4rnaが使った /add store への返答): [Embed] ✅ 店舗を追加しました`
  - スラッシュコマンドを使っても、使った人の発言は残らない。コマンドを使った記録は、Botの返答に書き添えた情報だけで、人が「/〜」と書いた発言はただの文字であることを、共通の指示に書く。AIが、文字で送った「/〜」をコマンドの実行と取り違えないようにするため。
  - あわせて、人の発言が「/」と英数字で始まるときは、本文の後に「(文字の発言で、コマンドの実行ではありません)」と書き添える。思考の深さが浅いと、共通の指示だけでは取り違えることがあったため。
- **時刻の表し方:** 日本時間で、曜日を付けて書く(例: `2026-10-27(火) 14:05`)。AIが道具で期間を指定するときも、日本時間として扱う。
- **今の日時の伝え方:** 人の発言に付けた時刻で伝える。話しかけた発言の時刻が、今にあたる。発言の形は毎回同じなので、キャッシュは崩れない。
- **発言者の名前:** サーバーのニックネームを優先し、なければDiscordの表示名、それもなければユーザー名を使う。
  - Discordから読み直したメッセージには、ニックネームが含まれない。保存した名前で補う。
  - 同じ人は、最後に分かった名前に揃える。
  - 話しかけたメッセージで分かった名前は、応答の仕事と一緒に渡す。保存の処理より先に応答の処理が動いても、ニックネームを使えるようにするため。

### サーバー全体の公開チャンネル

AIが、今いるチャンネルだけでなく、サーバーの公開チャンネルの過去のメッセージも、必要なときに道具で読めるようにする。決めた経緯は[issue #46](https://github.com/4rtoflow/Bobert/issues/46)を参照。
- **公開チャンネルの判定:** @everyoneのロールの権限に、チャンネルの@everyoneへの上書きを当てて計算する。「チャンネルを見る」と「メッセージ履歴を読む」の両方があれば公開チャンネル、それ以外は権限付きのチャンネル。
  - 「メッセージ履歴を読む」も条件にするのは、全員が過去の発言を読めるチャンネルだけを、ほかのチャンネルでの返答に使うため。
  - 公開スレッドとフォーラムの投稿は、親のチャンネルに従う。非公開スレッドと、年齢制限のチャンネル(と、その中のスレッド)は、権限付きとして扱う。
  - 認証の後に付くロールでチャンネルを見せているサーバーでは、公開チャンネルがなくなる。その場合、AIはほかのチャンネルの過去のメッセージを読めない。
  - 公開かどうかを判定できないチャンネル(情報を取れなかったときなど)は、権限付きとして扱う。
- **判定に使う情報:** Gatewayで、サーバー・チャンネル・スレッド・ロールの作成・変更・削除の通知を受け取り(`GUILDS`インテント)、チャンネルとスレッドの情報と、サーバーごとの@everyoneの権限をD1に記録する。記録にないチャンネル(通知より先にメッセージが届いたときなど)は、DiscordのAPIで確かめて記録する。古い通知で、新しい記録を上書きしない。
- **権限が変わったとき:** 通知を受けたときに判定し直す。公開チャンネルが権限付きに変わったら、そのチャンネル(中のスレッドを含む)の保存分を、D1とVectorizeから消す。権限付きから公開に変わったら、その後の新しいメッセージから保存し、前の分は`/import`で取り込む。
- **Botが止まっていた間の変更:** つながったときに届くサーバーの情報(`GUILD_CREATE`)の、全チャンネルの一覧と比べる。記録にあって一覧にないチャンネルは、削除されたとみなす。記録のないチャンネルの保存分(この仕組みの前に保存したものなど)は、DiscordのAPIで確かめ直し、権限付きか、確かめられなければ消す。
- **権限付きのチャンネルでの動き:** Botは今までどおり応答する。会話と、時系列で読む道具で読むそのチャンネルのメッセージは、Discordから直接読む(会話は、1回の返答でDiscordから読める100件まで)。意味で検索は、公開チャンネルだけを探す。会話の要約は保存する。要約は、その会話の続きの返答にだけ使い、検索やほかのチャンネルには出さない。
- **AIが読める範囲:** どのチャンネルで使っても、AIが読めるのは、今いるチャンネルと、公開チャンネルのメッセージだけ。道具の結果は、使うたびに、記録した公開・非公開で確かめる。保存分を消すのが遅れても、権限付きのチャンネルのメッセージを使わないようにするため。

### 過去メッセージを参照する道具(AIのツール)

AIには、過去メッセージを参照する道具を渡す。AIが必要と判断したときだけ呼び出し、Botが結果を返すと、AIはそれを踏まえて答える。対象は、今いるチャンネルと、サーバーの公開チャンネルのメッセージで、本人の過去の発言も、他の人の発言も含む。

| 道具             | できること                                                                                                                                                                                                                        |
| ---------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 意味で検索       | 検索語に関係するメッセージを最大10件探す。発言者や期間で絞り込める(例:「先月のAさんの発言」)。探す範囲は、このチャンネル(既定)か、サーバーの公開チャンネル全体かを選べる。検索語はWorkers AIでベクトルにし、Vectorizeで探す       |
| 時系列で読む     | 期間を日時で指定して、履歴を古い順や新しい順に読む(1回で最大50件)。基準のメッセージは、その時刻で指定する。ほかの公開チャンネル(スレッドを含む)も、名前で指定して読める。「このチャンネルで最初に話していたこと」などに答えられる |
| チャンネルの一覧 | サーバーの公開チャンネルの名前の一覧を返す。AIが、ほかのチャンネルの名前を確かめるのに使う                                                                                                                                        |
| 返信先を読む     | 会話の最初のメッセージが別のメッセージへの返信のとき、その返信先を古い方へたどって読む(最大50件)。会話の最初のメッセージが返信のときだけ渡す。「Bobertに聞く」で、説明するメッセージが返信のときに使う                            |
- **絞り込みの準備:** Vectorizeの各ベクトルに、発言者ID、時刻、サーバーIDを検索用の情報(メタデータ)として付ける(チャンネルは名前空間で分ける)。絞り込みに使う索引は、データを入れる前に作っておく必要がある(Vectorizeの制約)。サーバーIDを足す前に入れたベクトルは、管理用エンドポイント(`POST /admin/vectors/reindex`)で入れ直す。
- **時系列で読む道具の読み方:**
  - 期間は、日時(日本時間)で、より後(after)とより前(before)を指定する。どちらも省ける。
  - 新しい順(beforeからさかのぼる。既定)か、古い順(afterから)で読む。結果は、どちらでも古い順に並べる。
  - 読んだ件数で打ち切ったときは、続きを読むための日時(秒まで)を結果に添える。
  - 過去ログの取り込みが済んでいないチャンネルでは、保存していない期間があるので、Discordから読み、保存にも回す。
  - 読むチャンネルは、名前で指定する(先頭の「#」は外す)。省けば今いるチャンネル。読めるのは、今いるチャンネルと、公開チャンネル(スレッドを含む)だけ。同じ名前があれば、スレッドでないチャンネルを先に、古いものを選ぶ。
- **意味で検索の結果:**
  - 見つかったメッセージの本文は、D1から読む。消されたメッセージは、Vectorizeへの反映が遅れていても、結果に入らない。
  - Vectorizeは書き込みを数分後に反映するので、数分以内の発言は、まだ見つからないことがある。道具の説明にも、そう書いておく。
  - 結果は、近い順ではなく古い順に並べる。
  - サーバー全体を探すときは、メタデータのサーバーIDで絞り込む。権限付きのチャンネルでは、そのチャンネルのメッセージを保存していないので、範囲の指定にかかわらず、サーバー全体を探す。
  - 今いるチャンネル以外のメッセージには、チャンネルの名前を書き添える(例: `[2026-10-27(火) 14:05] #雑談 Alice: こんにちは`)。
- **渡し方:** 時系列で読む道具、意味で検索する道具、チャンネルの一覧の道具は、いつも渡す。返信先を読む道具は、会話の最初のメッセージが返信のときだけ渡す。道具の定義は、毎回同じ並び(時系列で読む、意味で検索、チャンネルの一覧、返信先を読む、Web検索)にする(キャッシュのため)。
  - チャンネルの一覧は、AIへの指示に入れずに、道具で渡す。チャンネルが変わってもキャッシュが崩れず、使わない返答では費用が増えないようにするため。
- **使い方の指示:** このサーバーやチャンネルのこと(ほかのBotや、以前に話していたことなど)は、Web検索より先に、道具で過去のメッセージを読んで調べるよう、共通の指示に書く。このチャンネルのほか、サーバーの公開チャンネルのメッセージも読めることも書く。
- **発言者の指定(意味で検索):** AIは、会話で見えている名前で指定する。Bobertは、保存したメッセージの名前から、その人を探す。
  - 前に使っていた名前でも見つかる。大文字と小文字は区別せず、先頭の「@」は外す。
  - 同じ名前の人が何人かいれば、全員を対象にする。見つからなければ、検索せずにそう伝える。
  - サーバー全体を探すときは、サーバー全体の保存したメッセージと名前から探す。
- **結果の渡し方:**
  - 会話と同じ形で、時刻と発言者の名前を付けて渡す(例: `[2026-10-27(火) 14:05] Alice: こんにちは`)。Bobertの発言も、同じ形で渡す。Embedの中身と、Botやコマンドの情報も、会話と同じように書き添える。
  - 検索結果は「資料」として扱い、その中に書かれた指示には従わないよう、共通の指示に書いておく。誰かが書き込んだ文が後で指示として効いてしまう、プロンプトインジェクションへの対策。
- **やり取りの流れ:** AIが道具を呼んだら、Bobertが実行して結果を返し、続きの答えを受け取る。道具を呼ぶ前の前置き(「調べます」など)は、答えに入れない。
- **回数の上限:** 1回の返答で、道具の呼び出しは合計5回まで。上限に達したら、道具を使わずに答えさせる。
- **費用:**
  - 道具を使ったときだけ、AIとのやり取りが往復分増える。
  - 2往復目以降の入力でも、それまでの部分にはキャッシュが効く。
  - 時系列で読む道具は、読んだメッセージの分だけ入力が増える。
  - 道具を使わないときは、追加の費用はかからない。
- **対応しないモデル:** 「その他」で入力されたモデルが道具に対応していない場合は、過去メッセージを参照せずに答える。候補の20個は、すべて道具に対応している。
- **今の実装:** 4つの道具(時系列で読む、意味で検索、チャンネルの一覧、返信先を読む)がある。

### 過去ログの取り込み(Botが動き出す前のメッセージ)

- **読んだ分だけ取り込む:** 次の場合は、その場でDiscordから取得してAIに渡し、同時に保存とベクトル化をする(保存するのは、公開チャンネルの分だけ)。
  - 時系列で読む道具が、まだ保存していない期間を読もうとしたとき
  - 保存していない古いメッセージへの返信で、Botに聞かれたとき
- **`/import`で全部取り込む:** 公開チャンネルの過去ログは、管理者が`/import`を実行したときに取り込む。
  - 対象は、公開チャンネルと、その中の公開スレッドとフォーラムの投稿(アーカイブされたものを含む)。取り込み済みのものは、取り込み直さない。
  - 実行できるのは、「サーバー管理」の権限を持つ人。Discordのコマンドの権限の既定(`default_member_permissions`)で決める。サーバー設定の「連携サービス」で変えられる。
  - DiscordのAPI(1回100件まで)で古い方へ順にたどり、Queuesで少しずつ進める。APIの利用制限を守るため、1回ごとに2秒の間を空ける。同時に取り込むチャンネルは5つまで(DiscordのAPIとWorkers AIの利用制限に当たらないように)。1つ終わるたびに、順番待ちのチャンネルを始める。
  - 進み具合(順番待ち、取り込み中、最後まで読んだ、取り込めなかった)と、どこまで取り込んだか、取り込んだ件数を、チャンネルごとに記録する。読む権限がなければ、取り込めなかったと記録する。
  - もう一度実行すると、次のものの取り込みを始める。まだ取り込んでいない公開チャンネル(後から公開に変わったものなど)、取り込めなかったもの、途中で止まったもの(最後の更新から10分たっても取り込み中のもの)。
  - 取り込み中に、もう一度実行されたときは、同じ取り込みの進み具合を、新しいメッセージでも見せる。同じチャンネルを二重には取り込まない。
  - 取り込めなかったチャンネルは、表示では知らせず、ログ(`missing_permission`)に残す。
  - 取り込みが終わるまでは、意味で検索できるのは取り込み済みの範囲だけ。
  - 初めて使われたチャンネルで自動で取り込む仕組みは、なくした(2026-10-28、#46)。取り込むかどうかと、その時期を、管理者が決められるようにするため。
- **進み具合の表示:**
  - 実行したチャンネルに、全員に見えるメッセージで出す。実行した人にだけ見えるメッセージは、実行から15分までしか書き換えられず、取り込みは15分を超えることがあるため。最初の15分はInteractionのトークンで、その後はBotのトークンで書き換える。
  - 取り込み中は、「取り込み中: 42% (ETA: 3:05)」だけを出し、5秒おきに書き換える。件数の見積もりが済むまでは「取り込み中: 0% (ETA: --:--)」。ETAは分:秒(秒は2桁)で、1時間を超えても分で続ける(例: 75:30)。
  - %は「その実行で取り込んだ件数 ÷ 見積もりの件数」。見積もりは、取り込みを始める前に、Discordのメッセージ検索のAPI(Search Guild Messages。2026-03-19からBotも使える)で、対象のチャンネルとスレッドを指定して数える(`total_results`)。見積もりは正確ではないので、完了するまでは99%で止める。サーバーの検索の準備がまだで数えられないとき(202、コード110000)は、終わったチャンネルの数で%を出す。
  - ETAは、直近1分の取り込みの速さから、残りにかかる時間を出す。進んでいなければ`--:--`にする。
  - 完了したら「取り込み完了: 9,123件」にする(その実行で取り込んだ件数。3桁ごとにカンマを入れる)。すべて取り込み済みなら「取り込み完了: 0件」。
  - 公開チャンネルがないときは「公開チャンネル(@everyoneが見られるチャンネル)がないため、取り込むものはありません。」、始められなかったときは「取り込みを始められませんでした。少し待ってから、もう一度試してください。」と出す。
  - 書き換えは、サーバーごとのDurable Objectが、アラームで行う。完了したら、見張るのをやめる。進み具合のメッセージは保存しない(会話ではなく、5秒おきに書き換わるため)。
- **費用:** 埋め込みとVectorizeの費用は運営者が負担する。目安は下の「保存と検索の費用」を参照。取り込むかどうかと、その時期は、管理者が`/import`で決める。
- **今の実装:** 読んだ分だけ取り込むのは、返信のつながりを読むとき(Botに聞かれたときと、返信先を読む道具)と、取り込みが済んでいないチャンネルで、時系列で読む道具を使ったとき。

### 保存と検索の費用

運営者が払う、Workersの基本料($5)を除いた追加の月額の目安。

| 保存件数                     | Vectorize          | D1  | 埋め込み(取り込み時に1回) |
| ---------------------------- | ------------------ | --- | ------------------------- |
| 約9,000件(2026-10時点の規模) | $0(含まれる範囲内) | $0  | 約$0.003                  |
| 10万件                       | 約$0.6             | $0  | 約$0.04                   |
| 100万件                      | 約$10              | $0  | 約$0.4                    |
- **前提:** 1024次元のベクトル(bge-m3)、検索は月1,000回、1メッセージ約30トークン、D1には索引込みで1件約1KB。
- **件数に比例して増える理由:** Vectorizeの検索料金は「(その月の検索回数+検索された索引の全件数)×次元数」で計算される。保存件数が増えるほど高くなる。
- **含まれる範囲:**
  - 保存は約1万件まで(1,000万次元)。
  - 検索は、件数と検索回数の合計が約4.8万まで(5,000万次元)。
- **費用を抑える方法(件数が増えたときの候補):**
  - チャンネルごとに索引を分ける。その月に検索されなかったチャンネルの分はかからない。
  - ベクトルの次元数を減らす。たとえば256次元にすれば、Vectorizeの費用はほぼ4分の1になる。候補はqwen3-embedding-0.6bで、上流の説明では先頭の一部の次元だけでも使える作りとされている。日本語での精度とあわせて要確認。

### プロンプトキャッシュ(会話全体を渡す費用を抑える)

- **並べ方:** 毎回同じになる部分を前に、毎回変わる部分を後ろに置く。変わる部分が前にあると、そこから後ろのキャッシュが効かなくなる。
  1. 道具の定義(過去メッセージの参照、Web検索)
  2. 共通の指示
  3. 本人の指示
  4. 会話の履歴(毎回同じ並び)
  5. 新しい発言

  `/feat`でWeb検索を切り替えるなどして道具の定義が変わると、その人のキャッシュは一度書き直しになる。
- **効き方(Anthropicの場合):**
  - キャッシュから読む分は、通常の入力料金の約1割(Opus 5.5は5%)。書き込みは通常の1.25倍。
  - キャッシュは5分間有効で、読まれるたびに延びる。5分以上間が空くと書き直しになる。1時間保持の設定もあるが、書き込みは通常の2倍。
- **キャッシュはキーの持ち主ごとに別:** 複数の人が交互に返信すると、それぞれが自分の分を書き込むことになる。
- **OpenRouter経由のモデル:** キャッシュの仕組みや対応の有無がモデルごとに違う(実装時に確認する)。
- **注意:** 既定のClaude Haiku 5.5は、入力が10万トークンを超えると単価が5倍($0.50/$2.50)になる。とても長い会話では、費用が跳ね上がる。

### 長い会話の自動要約

- **いつ:** 会話が、使うモデルの入力の上限の8割を超えたとき。上限はモデルごとに違う(多くは約100万トークン、Grok 4.7は50万トークン)。OpenRouterやAnthropicのモデル情報から取得する。
  - 候補と、「その他」で入力したOpenRouterのモデルは、OpenRouterのモデル一覧の上限(`context_length`)を使う。Anthropicで直接呼ぶ候補も、同じモデルの情報を使う。
  - 「その他」で入力したClaudeは、本人のキーで、Anthropicのモデル情報の入力の上限(`max_input_tokens`)を使う。
  - 上限が分からなければ、20万トークンとして扱う。
- **会話の量の測り方:** 直前の返答のときの、実際の入力のトークン数を使う。返す人のモデルが変わると多少ずれるが、2割の余裕で吸収できる。
  - 返答のたびに、会話全体を渡したときの入力のトークン数を、投稿した返答のメッセージごとに記録する(長い返答を分けたときは、どのメッセージにも)。道具やWeb検索で何回かに分けて呼んだときは、最初の1回の分(後の回には、道具の結果が入るため)。
  - 会話の中で、いちばん新しいBobertの返答の記録を使う。記録がなければ、要約しない。
- **どうする:**
  - 新しい20件を残し、それより前(前の要約を含む)を、そのときのモデルで要約してD1に保存する。返答の前に要約するので、その返答は少し遅くなる。
  - 要約を頼むときは、誰が何を言ったか、決まったこと、まだ決まっていないこと、大事な名前や数字、日時を残すように指示する。途中で打ち切られた要約は、大事なことが抜けているかもしれないので使わない。
  - 以降は「要約+それより後の発言」を渡す。要約は、会話の最初に、人の発言として渡す。要約で落ちた細かいところは、過去メッセージを参照する道具で読み直せる。要約があるときは、返信先を読む道具は渡さない。
  - 再び上限の8割を超えたら、もう一度要約する。
  - 「今すぐ要約」ボタンや右クリックメニューで要約するときも、範囲は同じ。
- **費用:** 要約を作る費用は、そのとき返信した人の負担。利用量の表示にも含める。保存した要約は、同じ会話に後から返信する人も使う。
- **仕組み:** 全モデル共通の独自の仕組みにする。Anthropicのサーバー側の自動要約機能(ベータ版)は使わない。
- **キャッシュへの影響:** 要約した直後は、渡す内容の先頭が変わるので、キャッシュが一度書き直しになる。
- **単価が上がるモデルでの案内:**
  - 入力が一定量を超えると単価が上がるモデルでは、その境目を超えたときに、要約を勧めるメッセージを送る。
  - 対象の例: Haiku 5.5(10万トークンで約5倍)、Grok 4.7(20万トークン)、GPT-6.1 SolとGPT-6 Astra(27.2万トークン)。
  - 境目は、候補なら候補の一覧の値、「その他」で入力したOpenRouterのモデルなら、価格の段階(入力のトークン数で単価が上がるもの)のうち、いちばん低いもの。「その他」で入力したClaudeは、単価が分からないので案内しない。
  - 境目を超えたかは、1回の呼び出しごとの入力で見る(単価の段階も、1回ごとに決まるため)。
  - 単価が変わらないモデルでは案内せず、上限の8割で自動要約するだけにする。
  - 案内は、その会話・その人・そのモデルで1回だけ、返答の末尾に添える(`compaction_notices`に記録)。長い返答を分けたときは、最後のメッセージに付ける。
  - 案内の文は「-# 会話が長くなり、入力が10万トークンを超えました。このモデルは、ここから料金が上がります。「今すぐ要約」で古い部分を要約すると、次からの費用を抑えられます。」(数は境目に合わせる)。小さな文字の行なので、会話の履歴からは外れる。
  - 案内には「今すぐ要約」ボタンを付ける。押した人のキーで要約し、費用もその人の負担。要約が済んだら、ボタンを消す(ほかの人が続けて押さないように)。
- **右クリックメニューからの要約:**
  - 会話の中のメッセージで、右クリックメニュー(アプリ)の「会話を要約」を選ぶと、そのメッセージまでの会話を要約する。境目を超える前でも使える。
  - 選んだ人のキーで要約し、費用もその人の負担。
- **ボタンとメニューで要約するときの流れ:**
  - 要約は長い会話で時間がかかるので、押した人(選んだ人)にだけ見える保留の応答をすぐ返し、応答用のQueueで要約する。終わったら、保留の応答を結果に書き換える。
  - 結果は「要約しました。次の返答から、要約と新しい20件の発言をAIに渡します。」。利用量の表示をONにしていれば、費用の行も付ける。
  - 新しい20件より前の発言がなければ、「この会話は、まだ要約するほど長くありません(新しい20件より前の発言がありません)。」と伝えて、要約しない。
  - キーがないとき、AIに断られたとき、エラーのときは、返答と同じ文で伝える。
  - 要約した後は、結果を書き換えられなくてもやり直さない(やり直すと、もう一度要約して費用がかかるため)。

## Discordの権限

- 特権インテント「Message Content」を必須とする(決定事項を参照)。Botが見えるチャンネルの全メッセージの本文が、Botに届く。
- メッセージの受信には、`GUILD_MESSAGES`インテントを使う。チャンネル・スレッド・ロールの変更の受信には、`GUILDS`インテント(特権ではない)を使う。
- `/import`で件数を見積もるメッセージ検索には、メッセージ履歴を読む権限と、Message Contentのインテントが要る(どちらも、すでに使っている)。アーカイブされたスレッドの一覧を読むのにも、メッセージ履歴を読む権限が要る。
- Botに必要な権限は、「チャンネルを見る」「メッセージを送信」「スレッドでメッセージを送信」「メッセージ履歴を読む」。応答するときに、返信のつながりをDiscordから読むため、メッセージ履歴を読む権限が要る。読めなかったときは、ログに`missing_permission`を残す。
- 寄付で答える前に、寄付した人がサーバーにいるかを、サーバーのメンバーを1人取得するAPIで確かめる。このAPIには、特権インテント(`GUILD_MEMBERS`)も、追加の権限も要らない。

## 開発と運用

- **環境:** 開発用と本番用を分ける。DiscordのBotアプリと、Cloudflareの環境(Worker、Durable Object、Queues、D1、Vectorize、シークレット)を2つずつ用意する。
- **テストとデプロイ:** GitHub Actionsで自動化する。プルリクエストでテストを実行し、mainに入ったら本番に自動でデプロイする。
- **ログ:** 会話の本文とキーは残さない。記録するのは、ユーザーID、時刻、モデル、トークン数、エラーの種類だけ。
- **障害の通知:** Gatewayが致命的なコードで切れたときなどは、開発者用のDiscordチャンネルに通知する。
- **技術構成:**
  - パッケージ管理はpnpm、テストはVitest(Cloudflare公式のWorkers用の連携を使う)、リントと整形はBiome。
  - 1つのWorkerプロジェクトに、Durable Object、Queueの処理、HTTPの受付をまとめる。

| 時刻をUTCで渡す                                     | ―        | AIが日本時間に直して考える必要があり、日付の境目で間違えやすいため                         |
